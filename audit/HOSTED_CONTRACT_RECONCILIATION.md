# Hosted contract reconciliation — proposed, 5 October 2026

**Not deployed.** This report compares current production Kotlin, canonical migration history, the first audit and the supplied real hosted metadata captured at **14:34:17 EAT on 5 October 2026**. The supplied JSON is retained in `hosted-contract-snapshot.json`; extracted definitions are in `hosted-functions/`. The proposed standalone migration is `supabase/migrations/202610050001_android_contract_reconciliation.sql`. Nothing here authorizes its automatic hosted execution.

## Findings that change the first audit

The first audit's hosted unknowns are now resolved for the objects in the snapshot:

- Both terms overloads are installed and executable by authenticated users. This is a confirmed HTTP API ambiguity, not evidence that Kotlin selects the integer body.
- Missing reviewed acceptance/edit/cancel RPCs are confirmed, along with missing grace/external recovery RPCs.
- Hosted `loans.lender_contribution` is integer NOT NULL without a default. The **installed old acceptance already supplies it correctly**; the canonical acceptance INSERT does not. The proposal preserves the hosted requirement explicitly.
- Hosted `loan_offers.borrower_id` is UUID NOT NULL without a default; no borrower-derivation trigger is installed. **Hosted creation explicitly supplies it correctly.** The proposal keeps that assignment; it never replays the canonical INSERT that omits it.
- Hosted profiles lack `profile_email`, the current four-argument completion API and phone uniqueness/validation helpers. The installed three-argument API returns the profile row and ignores its email argument.
- Hosted request creation reserves borrowing capacity before funding and supports only community requests. Canonical/current intended capacity uses funded outstanding principal and supports disclosed direct requests.
- Hosted repayment's active wrapper uses interest-first allocation and a separate `repayment_operations` table, while its internal `repay_loan` uses principal-first and inserts into a nonexistent `transactions.related_entity_id`. **Do not replace the working allocation simply because the canonical body differs.**
- The first audit's “cannot retry rejected connection” finding applies to canonical history; hosted `send_connection_request` already reuses a rejected/removed row. The proposal preserves this hosted behavior.
- The first audit's wallet-check failure was local: the hosted constraints do **not** include `locked_balance <= balance`. The active hosted repayment therefore can consume reserved money. The proposed RPC checks available funds explicitly, leaving existing constraints intact.

## Terms failure: exact resolution analysis

Current Kotlin sends POST RPC `request_loan_offer_terms` with named JSON keys `p_offer_id`, `p_interest_rate`, `p_period_days`. Rate and days are JSON numbers created from Int; the UUID is a JSON string. No SQL type cast, overload-specific argument name or custom routing is sent.

| Installed body | Authorization/state | Terms rule | Locking / message | Grants |
|---|---|---|---|---|
| `(uuid,integer,integer)` | auth present, offer borrower must equal auth.uid(), OFFERED only | nonnegative integer rate; **no upper/equal-or-lower check**, 7–365 days | offer first; generic notification; search_path public | authenticated yes, anon no |
| `(uuid,numeric,integer)` | auth present, selects own OFFERED offer | rate 0 through existing offer rate, 7–365 days | parent request then offer; named participant notification; empty search_path | authenticated yes, **anon yes** |

Both have **identical parameter names**. PostgREST does not implement PostgreSQL typed-SQL overload selection from Kotlin Int versus numeric JSON. With both loaded in its schema cache, this request has two candidates and fails with **PGRST203 / HTTP 300**. There is no valid conclusion that the current HTTP call deterministically executes the integer overload. A typed SQL Editor call using an integer literal can select the integer body, which would give misleading evidence about the Android path. [PostgREST function overloading](https://postgrest.org/en/v14/references/api/functions.html), [PostgREST errors](https://postgrest.org/en/latest/references/errors.html).

This is a **confirmed contract defect and strong probable cause** of the reported generic error. The exact failed attempt still lacks its HTTP/Logcat error and cache state, so it is not established that it returned PGRST203. Identical argument names have the same candidate set for different accounts; an earlier success could precede overload installation/cache reload, or use a different path. Account choice alone does not disambiguate them.

The proposal keeps ONE `(uuid,numeric,integer)` signature. Its intended behavior is chosen from current UI and policies: whole nonnegative rate no higher than the current offer; current 7–365-day negotiation range; borrower-only OFFERED state; request-first locking; valid/live parent; server profile gate; correct lender notification. It preserves 7% normal/15% approved direct offer ceilings. It explicitly drops `(uuid,integer,integer)`. Same-offer pending renegotiation remains rejected until lender response; another eligible offer remains independent. No new automatic overwrite of pending terms is introduced.

## Security review and precise scope

All 22 current app RPC names and the intentional legacy acceptance/profile compatibility APIs are authenticated-only except minimal boolean username availability (anon allowed). Definer RPCs explicitly check auth.uid(), enforce own borrower/lender/request recipient roles, use empty search_path and qualified application/Auth relations. Caller IDs are never accepted as replacements for authenticated identity.

Arbitrary-user/internal functions—Trust rewards/penalties, reliability calculation, statistics/capacity updates, offer release, internal repayment, phone/completeness checks, and trigger functions—have client execution revoked. Global maintenance/mark-overdue are executable only by trusted owner/service_role; authenticated refresh can target only auth.uid() and related borrower data through its fixed wrapper. Their internal body intentionally does not require an end-user JWT because cron/owner execution has none. This is privilege isolation, not pretending RLS protects a definer.

The hosted snapshot exposes `maintain_account_data`, `mark_loan_overdue`, `refresh_profile_limit` and `refresh_profile_statistics` to anon/authenticated. Some have no identity validation and can mutate arbitrary users. The proposal revokes those grants. PUBLIC inherited EXECUTE is revoked explicitly after replacement; grants are restored only from the reviewed allowlist.

Hosted direct client writes to profiles/requests/offers can bypass wallet/Trust RPC checks. The proposal revokes direct financial-table write privileges, grants current RLS SELECTs, and retains only `profiles UPDATE(full_name,username,bio,location,profile_image)` and `notifications UPDATE(read)`. Existing lender-preference owner policies/privileges are preserved. SELECT policies on profiles become owner-only; request SELECT becomes borrower/designated recipient/connected community, matching current Android's directory-based public lookup. This narrows access; no RLS is disabled and no table privilege is expanded. Other RLS/write policy definitions remain, but grants prevent the unsafe direct financial writes.

The snapshot lists named functions and related table triggers; it does **not** enumerate every public RPC or every Auth trigger. The proposal refuses an **unreviewed non-extension client-callable SECURITY DEFINER** function outside its allowlist. If live objects outside the captured scope trigger that assertion, review them before execution; do not suppress the assertion. The proposal also refuses unreviewed ALL policies on the two private-read tables. It does not claim unseen functions are safe.

## Exact proposed behavior changes

1. Remove terms ambiguity; retain equal-or-lower whole-rate bargaining, live parent validation and OFFERED-only submission. A second pending same-offer request stays rejected; different eligible offers remain independent. Lender response can return the offer to OFFERED. Negotiation may still extend to 365 days, as current UI allows; creation/edit stay capped at parent preferred period.
2. Provide missing reviewed acceptance/edit/cancel/grace/recovery APIs. Acceptance checks the displayed amount/rate/days, funds `min(offer amount,remaining request)`, explicitly writes contribution and original deadline, checks freeze/capacity/approval and closes/refunds **all** competing offers even on partial funding. Remaining amount can be funded by a subsequently created offer. Sender/recipient accounting and hosted LOAN_DISBURSEMENT label are retained.
3. Add future support reward/statistics refresh on acceptance; keep actual installed Trust formulas, point schedules, daily penalty receipts, reliability computation and projection bodies unchanged. Existing rewards/history are never replayed. Repeat completion is deduplicated with the retained trigger.
4. Edit reservation by exact delta. Cancel/decline/release require sufficient reserved balance and transition status before any repeat can succeed. **Cancel archives the offer as EXPIRED and retains notifications/history**, rather than deleting offers as the historical report did; pending lists remove it and a cancellation notification is emitted. This is an explicit preservation choice for review.
5. Support direct/above-limit request creation, notifications and current funded-debt capacity model. Creation no longer deducts unfunded request amounts. Edit remains within current capacity, releases old pending offers and clears the above-limit flag if the edited request is now within limit. Cancellation stores CANCELLED instead of deleting/restoring old request reservations.
6. Refresh now performs scoped catch-up and recomputes available capacity from funded outstanding principal. **Deployment does not call refresh or reset limits**; a later authenticated refresh can correct an old cached capacity that included unfunded reservations. Borrowing_limit/Trust policy is unchanged.
7. Repayment uses a single authorized implementation with **hosted interest-first allocation**, rejects overpayment as active hosted API did, protects reserved funds, writes loan_payments and correctly keyed transaction status/loan_id, consults old receipt storage and writes new UUID receipts atomically. It allows repayment of DEFAULTED debts. Request history statuses are no longer overwritten to REPAID by repayment; funding status remains separate from loan repayment status, matching canonical model and current separate UI lists.
8. Add one-time grace columns without backfilling financial rows. Existing GRACE_PERIOD status/audit history counts as previously granted; legacy effective deadlines remain respected. Future maintenance transitions debts to DEFAULTED after original +3 days or granted deadline; defaulted debts can be repaid or settled externally by their lender. No maintenance executes during migration.
9. Add contact email and canonical mobile uniqueness, phone-aware atomic profile completion and intentional old three-text compatibility; only an empty phone can be filled, an existing mobile cannot be changed through this API. ensure can hydrate an owner's empty email from Auth metadata/email at runtime. Auth UUID remains authoritative; no new Auth trigger/user creation scheme.
10. Narrow unsafe function/table privileges/private-read policies. Lender-preference behavior, 7/15 ceilings, hosted request expiry default (30 days), wallet/limit/profile defaults and existing validated constraints remain intact.

## Migration safety / prerequisites

The migration begins BEGIN and ends NOTIFY/COMMIT. It sets local lock/statement timeouts. All failures roll back the whole transaction. It does not invoke financial/Trust helpers during deployment; no top-level money, loan, offer, request, reward or limit data edits occur.

Prerequisite assertions: owner execution, all required RLS-enabled tables/functions, enabled original deadline/Trust-initialization triggers, receipt column types, nonnegative and balanced wallets, request/loan accounting, offer participant agreement, exact pending-offer reservation totals, duplicate receipt IDs, unexpected required INSERT fields and unreviewed callable definers/policies/overloads. Incompatible legacy receipt storage aborts. The missing canonical contribution column can be added only to an **empty** loans table; an existing populated database without it aborts instead of silently backfilling. Hosted contribution remains integer NOT NULL with no invented default.

Additive fields are profile_email default empty, nullable grace timestamp/days and—only on an empty fresh loans table—the required contribution. Index creation may scan/lock tables; duplicate canonical phones abort rather than merge accounts. Existing index names are not evidence of equivalent definitions; review/run the negative tests and assertions if deployment reports drift. Runtime money operations include Int bounds rather than broadening checks. No constraints are dropped, tables truncated, users/loans/offers deleted, wallets reset, scores/limits reset, rows backfilled, histories rebuilt or RLS disabled.

No historical migration/report SQL is recommended for hosted replay. Historical files were used to understand intended behavior and to construct local tests only. `dashboard_setup.sql` and the old dashboard generator still represent the earlier interest-only release: **do not regenerate or run that SQL as this deployment**. The authoritative proposed deployment artifact is the new standalone migration. Publication of a revised dashboard artifact belongs after review, not this preparation step.

## Rollback strategy

See `RECONCILIATION_ROLLBACK_STRATEGY.md`. Before COMMIT, an assertion/dependency/type/uniqueness failure rolls back every change. After a committed rollout with new financial actions, **do not run historical rollback blocks**: they do not know about new ledger receipts and can charge retries again or recreate overload ambiguity. Retain ledgers/new columns/receipt bridge and repair narrowly with a reviewed forward patch. Preserve the current snapshot plus a deployment-time schema-only export as rollback evidence; never restore financial rows from an old dump over live activity.

**Stop here for review.** Proposed SQL exists and local evidence is available; no hosted execution was attempted. Prerequisite failure is a review/data-consistency finding, not permission to weaken constraints, release reservations or reset accounts.
